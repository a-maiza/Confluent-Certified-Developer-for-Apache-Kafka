🤝 TLS Handshake — etapes detaillees
1
ClientHello
Le producer initie la connexion TCP puis le handshake TLS. Il envoie la liste des cipher suites supportees, la version TLS max, et un nonce aleatoire (client_random).
Producer→Broker
Contient : TLS version, cipher suites, client_random, SNI
Fichier utilise : aucun
2
ServerHello + Certificate
Le broker choisit le cipher suite, genere son nonce (server_random) et envoie son certificat public depuis son keystore. Envoie aussi ServerKeyExchange si ECDHE.
Broker→Producer
Source : Keystore broker (certificat public)
Verifie par : Truststore producer (CA)
Verifie aussi : CN/SAN = hostname du broker
3
CertificateRequest (mTLS)
Si ssl.client.auth=required, le broker demande le certificat du producer et envoie la liste des CA acceptees pour que le producer sache quel certificat presenter.
Broker→Producer [ mTLS uniquement ]
Declenche par : ssl.client.auth = required/requested
Contient : Liste CA acceptees par le broker
4
ClientKeyExchange + Certificate
Le producer genere le pre-master secret, le chiffre avec la cle publique du broker, et envoie son propre certificat public si mTLS est requis.
Producer→Broker
Source : Keystore producer (certificat public — mTLS)
Verifie par : Truststore broker (CA)
5
CertificateVerify (mTLS)
Le producer signe le transcript du handshake avec sa cle privee (ssl.key.password). Le broker verifie cette signature avec la cle publique du certificat producer. Preuve de possession de la cle privee.
Producer→Broker [ mTLS uniquement ]
Utilise : Cle privee producer (keystore)
Algo : RSA-PSS ou ECDSA selon le certificat
6
Master Secret → Cles de session
Les deux parties derivent le master secret depuis client_random + server_random + pre-master. Puis generent les cles de session AES symetriques pour chiffrer le trafic.
Producer↔Broker [ calcul local des deux cotes ]
Resultat : 4 cles symetriques (write/read x client/server)
Algo : AES-128-GCM ou AES-256-GCM
✓
Finished — Canal chiffre etabli · Produce / Consume
Les deux parties s'envoient un message Finished chiffre avec les nouvelles cles de session pour confirmer le handshake. Tous les messages Kafka suivants (ProduceRequest, FetchRequest, metadata...) sont chiffres avec AES-GCM. Les cles asymetriques (keystore) ne sont plus utilisees jusqu'a la prochaine connexion.
Producer↔Broker
Chiffrement : AES-128-GCM ou AES-256-GCM (symetrique)
Integrite : HMAC-SHA256 ou SHA384 selon cipher suite
Session : Duree configurable via ssl.session.timeout.ms
⚙️ Parametres SSL — detail complet
🔑 ssl.key.password
Type : string · Scope : Producer + Broker
Mot de passe protegeant specifiquement la cle privee a l'interieur du keystore. Optionnel : si absent, ssl.keystore.password est utilise. Permet une securite a deux niveaux.
⚠️ Si compromis : la cle privee est exposee → usurpation d'identite possible
ssl.key.password=my-key-secret-456
📁 ssl.keystore.location
Type : string (chemin) · Scope : Producer + Broker
Chemin absolu vers le fichier keystore (.jks ou .p12) contenant la cle privee et le certificat public. Doit etre lisible par le processus Kafka. Preferer PKCS#12 (plus portable).
⚠️ Si absent cote broker : TLS impossible. Cote producer : mTLS impossible
ssl.keystore.location=/etc/kafka/certs/producer.p12
🔐 ssl.keystore.password
Type : string · Scope : Producer + Broker
Mot de passe pour ouvrir le fichier keystore entier. Requis des que ssl.keystore.location est defini. Premier niveau de protection du fichier .jks/.p12.
⚠️ Si compromis : acces au fichier keystore (cle privee encore protegee par ssl.key.password)
ssl.keystore.password=keystore-pass-123
🏛️ ssl.truststore.location
Type : string (chemin) · Scope : Producer + Broker
Chemin absolu vers le fichier truststore contenant les certificats des CA de confiance. Utilise pour valider le certificat de l'interlocuteur lors du handshake TLS.
⚠️ Si absent cote producer : impossible de valider le broker → connexion refusee
ssl.truststore.location=/etc/kafka/certs/truststore.jks
🛡️ ssl.truststore.password
Type : string · Scope : Producer + Broker
Mot de passe pour ouvrir le fichier truststore. Protege l'integrite des CA de confiance. Si un attaquant modifie le truststore sans ce mot de passe, la falsification est detectee.
⚠️ Si compromis : modification possible des CA de confiance → attaque MITM
ssl.truststore.password=truststore-pass-789
🔒 ssl.client.auth
Type : string · Scope : Broker uniquement
Controle si le broker exige un certificat client. none = TLS simple, requested = demande mais optionnel, required = mTLS obligatoire. Cle de l'activation du mTLS.
⚠️ none = pas d'authentification producer. required = tous les producers doivent avoir un certificat valide
ssl.client.auth=required # none | requested | required
🔀 TLS simple vs mTLS — quelle difference ?
TLS Simple (One-Way)
ssl.client.auth = none
✅ Producer possede un truststore (valide le broker)
❌ Producer n'a PAS besoin de keystore
✅ Broker possede un keystore (presente son cert)
❌ Broker n'a PAS besoin de truststore
🔐 Chiffrement du trafic : OUI (AES-GCM)
👤 Authentification producer : NON
🎯 Cas d'usage : chiffrement seul, sans ACL certificat
Le broker ne sait pas QUI se connecte, seulement que la connexion est chiffree.
mTLS (Mutual TLS)
ssl.client.auth = required
✅ Producer possede un truststore ET un keystore
✅ Broker possede un keystore ET un truststore
🔐 Chiffrement du trafic : OUI (AES-GCM)
👤 Authentification producer : OUI (via certificat)
🎯 Cas d'usage : production securisee, zero-trust
⚙️ Compatible ACL Kafka par CN du certificat
Le broker sait exactement QUI se connecte et peut autoriser/refuser selon le CN du certificat.
🚨 Erreurs SSL courantes & solutions
❌ SSL handshake failed
Cause : Le producer ne peut pas valider le certificat du broker. La CA du broker n'est pas dans le truststore producer.
✅ Fix : Importer le cert CA du broker dans ssl.truststore.location du producer
❌ Certificate expired
Cause : Le certificat du broker ou producer a depasse sa date de validite. Arret complet de toutes les connexions SSL.
✅ Fix : Renouveler le certificat et recharger le keystore (rolling restart)
❌ PKIX path building failed
Cause : Chaine de certificats incomplete. Certificat intermediaire manquant dans le keystore ou truststore.
✅ Fix : Inclure la chaine complete CA-root → CA-inter → cert dans le keystore
❌ No subject alternative names
Cause : Le hostname du broker ne correspond pas au CN/SAN du certificat. La verification hostname echoue.
✅ Fix : Ajouter le SAN correct au certificat ou desactiver ssl.endpoint.identification.algorithm (non recommande)
❌ SSLPeerUnverifiedException
Cause mTLS : Le broker a recu un certificat producer non signe par une CA de son truststore.
✅ Fix : Importer la CA producer dans le truststore broker, ou verifier ssl.client.auth
❌ Keystore was tampered with
Cause : Mauvais ssl.keystore.password, ou fichier keystore corrompu / incompatible (JKS vs PKCS12).
✅ Fix : Verifier le mot de passe avec : keytool -list -keystore fichier.jks
