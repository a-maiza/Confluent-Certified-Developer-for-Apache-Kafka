🔑 sasl.mechanism — Les mecanismes d'authentification
PLAIN
Username + Password en base64
💬 Envoie username/password en clair (base64 non chiffre)
⚠️ Doit absolument etre combine avec SSL (SASL_SSL)
✅ Simple a configurer, compatible partout
⚙️ Login module : PlainLoginModule
🎯 Cas d'usage : dev/test, cloud managed Kafka
Facile mais risque si sans TLS. Toujours utiliser SASL_SSL.
GSSAPI (Kerberos)
Generic Security Services API
🏰 S'appuie sur un KDC (Key Distribution Center)
🎪 Tickets Kerberos, pas de mots de passe transmis
✅ Authentification mutuelle native
⚙️ Login module : Krb5LoginModule
📌 Necessite sasl.kerberos.service.name
🎯 Cas d'usage : enterprise, Hadoop/HDP, LDAP/AD
Le plus securise pour les entreprises avec Active Directory / KDC.
SCRAM-SHA-256/512
Salted Challenge Response Auth
🧪 Challenge-response, jamais le mdp en clair
🔒 Creds stockes hashes + sales dans Zookeeper/KRaft
✅ Resistance aux attaques replay et MITM
⚙️ Login module : ScramLoginModule
🎯 Cas d'usage : sans Kerberos, securite renforcee
Meilleur compromis securite/simplicite sans infrastructure Kerberos.
OAUTHBEARER
OAuth 2.0 Bearer Token
🔑 Utilise des JWT Bearer tokens OAuth 2.0
🔁 Tokens a courte duree de vie (expiration auto)
✅ Ideal pour microservices et cloud-native
⚙️ Necessite sasl.login.callback.handler.class
🎯 Cas d'usage : K8s, cloud (MSK, Confluent Cloud)
Standard moderne pour les architectures cloud et microservices.
⚙️ Parametres SASL — detail complet
🔑
sasl.mechanism
TYPE: string · SCOPE: Producer + Consumer + Broker
Definit le protocole SASL utilise pour s'authentifier. Doit correspondre exactement a ce que le broker declare dans sasl.enabled.mechanisms. La valeur est case-sensitive.
PLAINUsername/password base64 — necessite TLS
GSSAPIKerberos — entreprise, Active Directory
SCRAM-SHA-256Challenge-response — recommande
SCRAM-SHA-512SCRAM avec hash plus fort
OAUTHBEARERJWT OAuth 2.0 — cloud-native
⚠️ Mismatch avec le broker = connexion refusee avec SASL authentication failed
sasl.mechanism=SCRAM-SHA-256
📋
sasl.jaas.config
TYPE: string (JAAS) · SCOPE: Producer + Consumer
Configuration JAAS (Java Authentication and Authorization Service) en ligne. Specifie le LoginModule a utiliser et ses options. Remplace le fichier jaas.conf externe. Contient les credentials.
LoginModuleClasse Java qui gere l'auth (PlainLoginModule, Krb5LoginModule...)
required/optionalNiveau de contrainte du module
Optionsusername, password, keyTab, serviceName...
⚠️ Contient les credentials — ne jamais logger ou exposer cette valeur
🛡️
security.protocol
TYPE: string · SCOPE: Producer + Consumer + Admin
Protocole de communication avec le broker. Combine ou separe chiffrement (TLS) et authentification (SASL). Doit correspondre au listener configure sur le broker (listeners= dans server.properties).
PLAINTEXTAucune securite — dev local
SSLTLS uniquement, pas de SASL
SASL_PLAINTEXTSASL sans TLS — reseau interne
SASL_SSLSASL + TLS — recommande production
⚠️ Doit correspondre exactement au listener broker sinon Connection refused
security.protocol=SASL_SSL
🔍
ssl.endpoint.identification.algorithm
TYPE: string · SCOPE: Producer + Consumer + Admin
Algorithme de verification du hostname du broker dans son certificat SSL. Quand defini a "https", verifie que le CN ou un SAN du certificat correspond au hostname de connexion. Protege contre les attaques MITM.
httpsVerification hostname active (RECOMMANDE)
(vide "")Verification desactivee — DANGEREUX en prod
⚠️ Desactiver = vulnerable aux attaques Man-In-The-Middle meme avec TLS actif
ssl.endpoint.identification.algorithm=https # Pour desactiver (dev uniquement): ssl.endpoint.identification.algorithm=
🔧
sasl.login.callback.handler.class
TYPE: class · SCOPE: Producer + Consumer
Classe Java personnalisee implementant AuthenticateCallbackHandler pour gerer les challenges SASL. Utile pour OAUTHBEARER (recuperer/renouveler un token JWT), ou pour des systemes d'auth custom.
nullHandler par defaut (PLAIN/SCRAM/GSSAPI)
Custom classPour OAUTHBEARER ou auth non standard
Confluentio.confluent.kafka.clients.plugins.auth.token.TokenUserLoginCallbackHandler
⚠️ Classe mal implementee = fuite de credentials ou echec auth silencieux
sasl.login.callback.handler.class=\ com.example.CustomOAuthCallbackHandler
🏰
sasl.kerberos.service.name
TYPE: string · SCOPE: Producer + Consumer (GSSAPI)
Nom du service Kerberos du broker Kafka. Utilise pour construire le SPN (Service Principal Name) sous la forme kafka/hostname@REALM. Doit correspondre exactement au principal enregistre dans le KDC.
Valeur type"kafka" (defaut Kafka)
SPN construitkafka/broker-host.domain@REALM
Cote brokerdoit matcher sasl.kerberos.principal
⚠️ Mismatch avec le KDC = GSS initiate failed / kinit errors
sasl.kerberos.service.name=kafka # SPN resultant: kafka/broker.corp.local@CORP.LOCAL
📋 sasl.jaas.config — Exemples par mecanisme
PLAIN — Username/Password
org.apache.kafka.common.security.plain.PlainLoginModule
sasl.jaas.config=org.apache.kafka.common.security.plain.PlainLoginModule required username="my-producer" password="my-secret-password"; # ATTENTION : le point-virgule final est OBLIGATOIRE # Toujours combiner avec security.protocol=SASL_SSL
SCRAM-SHA-256 — Challenge-Response
org.apache.kafka.common.security.scram.ScramLoginModule
sasl.jaas.config=org.apache.kafka.common.security.scram.ScramLoginModule required username="my-producer" password="my-secret-password"; # Le mdp ne transite JAMAIS en clair (challenge-response) # Enregistrer le user cote broker : # kafka-configs.sh --alter --add-config \ # 'SCRAM-SHA-256=[password=my-secret-password]' \ # --entity-type users --entity-name my-producer
GSSAPI — Kerberos (keytab)
com.sun.security.auth.module.Krb5LoginModule
sasl.jaas.config=com.sun.security.auth.module.Krb5LoginModule required useKeyTab=true storeKey=true keyTab="/etc/security/keytabs/producer.keytab" principal="producer@CORP.LOCAL"; # sasl.kerberos.service.name=kafka obligatoire # Le keytab est genere par l'admin Kerberos/AD
OAUTHBEARER — JWT Token
org.apache.kafka.common.security.oauthbearer.OAuthBearerLoginModule
sasl.jaas.config=org.apache.kafka.common.security.oauthbearer.OAuthBearerLoginModule required; # La logique de token est dans le callback handler : sasl.login.callback.handler.class=com.example.OAuthCallbackHandler # Le handler recupere le JWT aupres du serveur OAuth # et le renouvelle avant expiration automatiquement
🏰 Flux Kerberos (GSSAPI) — Comment ca fonctionne
1
AS-REQ — Demande TGT
Le producer s'authentifie aupres du KDC avec son keytab. Il recoit un Ticket Granting Ticket (TGT) chiffre. Aucun mot de passe ne transite.
Producer→KDC
2
TGS-REQ — Demande Service Ticket
Le producer presente son TGT au KDC et demande un ticket de service pour kafka/broker-host@REALM (SPN construit depuis sasl.kerberos.service.name).
Producer→KDC
3
TGS-REP — Reception Service Ticket
Le KDC retourne un Service Ticket chiffre avec la cle secrete du broker Kafka. Le producer ne peut pas le lire — seul le broker peut le dechiffrer.
KDC→Producer
4
AP-REQ — Presentation au Broker
Le producer envoie le Service Ticket au broker Kafka. Le broker le dechiffre avec son keytab et valide l'identite du producer. Auth mutuelle complete.
Producer→Broker
5
Session etablie
Le broker confirme l'authentification. La session est etablie avec des cles de session derivees. Les tickets Kerberos ont une duree de vie limitee (typiquement 8-24h).
Broker→Producer

Le flux OAUTHBEARER implique 3 entites : le Producer/Consumer, le Authorization Server (AS) (ex: Keycloak, Okta, Azure AD), et le Broker Kafka.

1
Token Request — Client Credentials Grant Producer → Auth Server
Le Callback Handler appelle le endpoint /token de l'Authorization Server via HTTP POST avec les credentials du client (client_id + client_secret ou certificate). C'est le seul moment ou les credentials sont utilises.
POST https://auth-server/token
grant_type=client_credentials
client_id=kafka-producer-app
client_secret=s3cr3t
scope=kafka-read kafka-write
2
Token Response — Reception du JWT Auth Server → Producer
L'Authorization Server retourne un JWT (JSON Web Token) signe avec sa cle privee. Le JWT contient : l'identite du producer (sub), les scopes/permissions, et la date d'expiration (exp).
HTTP 200 OK
{
  "access_token": "eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJrYWZrYS1wcm9kdWNlci1hcHAiLCJzY29wZXMiOlsia2Fma2Etd3JpdGUiXSwiZXhwIjoxNjk5OTk5OTk5fQ.SIGNATURE",
  "token_type": "Bearer",
  "expires_in": 3600
}
Header: algo + type
Payload: sub, scopes, exp, iat
Signature: RS256 / ES256
3
SASL Handshake — Envoi du JWT au Broker Producer → Broker
Le producer envoie le JWT Bearer Token au broker dans le message SASL OAuthBearerClientInitialResponse. Le token voyage dans la couche SASL, protege par TLS (SASL_SSL). Le broker ne connait pas le client_secret.
4
Validation JWT par le Broker Broker → Auth Server (JWKS)
Le broker valide la signature JWT en recuperant la cle publique de l'Authorization Server via l'endpoint /jwks (JSON Web Key Set). Il verifie aussi : expiration (exp), issuer (iss), audience (aud).
✅ Verifications
Signature RS256/ES256
exp > now()
iss = auth server URL
aud = kafka
❌ Rejete si
Signature invalide
Token expire
Mauvais iss ou aud
Token revoque
5
✅ Session etablie — Produce / Consume Broker → Producer
Le broker accepte la connexion. L'identite du producer est connue (sub du JWT). Les ACL Kafka peuvent etre basees sur le sub ou les scopes du token. La session dure jusqu'a expiration du token.
↻
Renouvellement automatique du token Callback Handler (background)
Avant expiration du JWT, le Callback Handler redemande automatiquement un nouveau token a l'Authorization Server (retour etape 1). Sans cela, le producer est deconnecte a l'expiration. Le parametre sasl.login.refresh.buffer.seconds controle la marge de renouvellement.
⚠️ sasl.login.refresh.buffer.seconds=30 (defaut) — renouvelle 30s avant expiration
📋 Configuration complete OAUTHBEARER
# Protocole
security.protocol=SASL_SSL
sasl.mechanism=OAUTHBEARER

# Module JAAS (vide — logique dans le handler)
sasl.jaas.config=org.apache.kafka.common.security.oauthbearer.OAuthBearerLoginModule required;

# Callback Handler — recupere et renouvelle le token
sasl.login.callback.handler.class=com.example.OAuthCallbackHandler

# Cote broker — valide le token JWT
sasl.server.callback.handler.class=com.example.OAuthValidatorHandler

# Renouvellement (30s avant expiration)
sasl.login.refresh.buffer.seconds=30
sasl.login.refresh.min.period.seconds=60

🚨 Erreurs SASL courantes & solutions
❌ SASL authentication failed
sasl.mechanism du client ne correspond pas a sasl.enabled.mechanisms du broker, ou credentials incorrects.
✅ Verifier la coherence des mecanismes et les credentials dans sasl.jaas.config
❌ Connection refused / listener not found
security.protocol du client (ex: SASL_SSL) ne correspond pas au listener configure sur le broker.
✅ Verifier listeners= et advertised.listeners= dans server.properties du broker
❌ GSS initiate failed (Kerberos)
sasl.kerberos.service.name incorrect, keytab expire, ou SPN kafka/hostname@REALM non enregistre dans le KDC.
✅ Verifier kinit -kt producer.keytab et le SPN avec klist -e
❌ SSL hostname verification failed
ssl.endpoint.identification.algorithm=https actif mais le hostname de connexion ne correspond pas au CN/SAN du certificat broker.
✅ Ajouter le hostname comme SAN dans le certificat broker (regenerer le cert)
❌ IllegalArgumentException: No JAAS config
sasl.jaas.config absent ou mal formate (point-virgule final manquant, espace avant le ;).
✅ Le point-virgule final de la config JAAS est OBLIGATOIRE : ...password="x";
❌ OAuthBearer token expired
Le callback handler OAUTHBEARER ne renouvelle pas le token avant son expiration. Le producer est deconnecte.
✅ Implenter le rafraichissement proactif dans le callback handler (avant expiry)
